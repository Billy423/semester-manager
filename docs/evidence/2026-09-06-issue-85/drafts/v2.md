### 1. Definition

**Routing is the resolving half of the query: a system-held function from an intent to the set of addresses that satisfy it.**

```
routing : intent -> { address }
```

The query has two halves. **Fetch** takes an address and returns its render - `look_at(id)`, a read, not routing. **Resolve** takes an intent the caller can state in the skeleton's structural vocabulary and returns the addresses that satisfy it. Routing is resolve.

**Who holds what.** The system holds routing. The coordinator holds two things: the intent it forms, and one routing result resident by policy - ring 0 (§6). A dispatch target holds nothing (`CONTEXT.md`, *holder*). No new holder is introduced.

**Spontaneity, restated as a mechanism.** Routing is not prompt-driven, and *unprompted* does not mean *without the owner*: it means **the intent must be formable from what the current render exposes**. The vocabulary reaches the coordinator in-band - `0098` spells names back, `0092`'s `has-more` lists a node's link kinds, `0096`'s `<edge>` carries `type` and `direction` - so `look_at` is this system's introspection. The coordinator never needs the schema out of band.

**What routing is not.** Not a search (`0046`: the coordinator *"does not search the corpus"*); not the delivery of an answer (that is fetch); not a judgment of importance (a judgment is made *with* operations and can never be an element of an operation set); not a statement about renders (what a render must carry so that an intent can be formed from it is stated here as a criterion, §4; what it looks like is #82's). Mechanistic reachability - that a path exists in the skeleton - is a property of the schema and not routing's: `0012`'s link table reaches the second and third of `CONTEXT.md`'s three answerability targets, and the first, *what is owed*, is the `obligation` kind itself. Reachability is deliberately not universal; two unrelated nodes may coexist.

### 2. Input - deliverable 1

**Routing's input is one intent, stated in the skeleton's structural vocabulary.** Not *ring 0 plus the skeleton index* as the body guessed - that is what the coordinator sees, not what routing consumes.

**The vocabulary, from `CONTEXT.md`'s definitions:** a **node** is a kind, an id and that kind's field set; a **link** is its own record, `from · to · kind · role? · locator?` (`0017`), never a field on either end (`0016`); **link kinds** are a closed set with endpoint signatures (`0012`); **direction** is `points-at` or `pointed-by` (`0096`); a **Ref** is `(kind, id)`, resolvable without a lookup (`0018`). The vocabulary contains no set operations and no content.

**What that vocabulary can describe, derived term by term.** A set of nodes can be named by kind; by a Ref; by a predicate over a node's own fields, where the field's type decides the comparisons (a moment admits a range, an enum equality, a bool identity) and boolean connectives join them; by a predicate over the link kinds a node participates in, which the system already projects per node as `has-more` (`0092`); by following a link kind in a direction to the other end, which is where the system draws the line between *what kinds of link* (`has-more`) and *linked to whom* (`<neighbours>`, `0096`; *one-hop traversal* is a persistence-tier primitive, `0059`); by a predicate over the link's own fields before crossing it (`spec` carries `role`, `0012`; `locator` is on every link, `0017`); and by repeating a crossing. Nothing else in the vocabulary names a set.

**The domain, as chain steps and predicate atoms:**

```
START(K)                 every node of kind K
START(ref)               the node this (kind, id) names, or nothing
FILTER(P)                keep the members satisfying P
MOVE(L?, D?, Q?)         cross links of kind L in direction D to the other end; Q filters on the link's fields;
                         L and D omitted means every kind, both directions
REPEAT(MOVE)             cross zero or more times

P ::= <field> <comparison> <value>  |  has(L, D)  |  has-no(L, D)  |  P and P  |  P or P  |  not P
```

**Composition is chaining**: each step's output set is the next step's input set, in one call. Set operations are not composition; they are not in the vocabulary, and the predicate connectives cover conjunction and disjunction inside a step while `has-no` covers the case difference would have served. `0060`'s *going one level deeper is one more call* is about depth - fetching a block - and a chain widens the address set without deepening any render, so the two do not meet.

**Two starts, deliberately.** `START(K)` and `START(ref)` name a set the same way in extension - `START(ref)` is `START(K) · FILTER(id = X)` - and neither derives from the other in the vocabulary. Spontaneity starts from ring 0, which is a set of rows and not a node, so its first intent is `START(K)`; a prompted walk from a node the coordinator is looking at is `START(ref) · MOVE`. What Q11 in the session called *anchored* and *unanchored* are these two starts, not two kinds of operation. A ring 0 row carries an id (`0025`: every read returns its ids), so an intent formed from ring 0 may also anchor.

**Outside the domain by type:** an intent by content. `P` has no content atom, so *things about X* cannot be stated. Who serves such an intent, and with what, is #87's.

**A candidate step this vocabulary places but does not admit:** the store's by-handle read, *"the chunks a known node points at"* (`CONTEXT.md`). A chunk is not a node and the coupling is one field, `chunk.node_id` (`0019`), so it is not a `MOVE`; it is a step onto the other persisted thing. Whether it enters routing's domain is #87's.

**Not decided here:** the spelling of any step (`0070`); whether the two starts, or any step, are one surface verb or several (the grammar - #84's *Destination* names it a later decision); whether an edge's `id` shares the node id space. On the last: `0025`'s one space is *"shared by every kind that can be a link endpoint"*, which a link is not, and no record states where an edge's id comes from. This bears on `START(ref)` and is pointed at from here.

### 3. Output - deliverable 2

**Routing returns a set of addresses, each carrying what decides whether it is worth the next call.** Not bare ids: an assigned id *"says nothing about the record it names"* (`0089`, whose own scope is obligations' assigned ids; `course.id` is supplied, `0026`), so an address alone gives no basis to decide. What decides the call is a per-kind field set, ruled per kind (`0095`: *"one ruling per kind"*), and a member reached by `MOVE` also carries the link it was crossed by - `type`, `direction`, and the link's fields.

**What that looks like is #82's.** In a block a member renders as a line inside an `<edge>` (`0096`); in ring 0 it renders as a row; the two are not the same field set (`0038`'s band A carries `optional`, `done_by` and `has-more`, which the line does not), and this record does not say which fields either carries.

**The set is unordered.** Arrangement is a render clause (`0041` grounds order on the material; `0100` places it with ring 0's render).

**The body's trichotomy is not three alternatives.** The output is a set. *Dispatch* is the form `0039` selects when the set is unaffordable to observe symmetrically. *Layer entry* is an intent over a different persisted thing, not a different kind of output. Nothing routing returns is an entry point into anything.

**An empty result names its boundary.** `0081`: routing returning `{}` carries what it ranged over - the kind, the source, the link kind. `0081` is a rule about the form of a negative answer and grounds nothing else in this record.

**Cost.** `START(ref) · MOVE` is O(degree) (`0046`). `START(K)` is O(kind). Whether a result can be observed is `0039`'s decision over the judgment's set, not routing's. Ring 0's roughly-55 is one such `0039` judgment held resident; it is not a bound on routing, and it carries `0038`'s scope clause and the fall26 caveat.

### 4. The necessity test - deliverable 3

**The premise, from the definition.** Routing serves a judgment. `0039` scopes a judgment to *"the set the judgment ranges over"* and permits observing it only symmetrically; `0043` drops what a return carried once it is used. Together: a set that arrives across several calls is never observed as a set, because the earlier members are gone before the later ones arrive. **So the unit is one return.** Billy's effectiveness constraint - the coordinator's call count may not grow with the graph - is the engineering face of the same premise.

> **A step or atom belongs in routing's domain if and only if some judgment the coordinator must make ranges over a set that no finite chain of the other steps and atoms produces in one return.**

**A stated limit.** The test admits by extension - by what set is produced. Two spellings of the same set are one operation to it. It therefore does not distinguish `START(K) · FILTER(id = X)` from `START(ref)`, and it must not be read as deciding that either spelling is absent from a surface; spelling is the grammar's.

**The test, run:**

| step / atom | a judgment the coordinator must make | without it | verdict | instance |
|---|---|---|---|---|
| `START(K)` | what is owed, across five courses | nothing else produces a set from nothing | in | ring 0's range |
| field comparison, connectives | which obligations are in course C; `0042`'s three triggers (two ranges and a disjunction) | `START` names only a kind; `course` is a field, not a link (`0029`), so no crossing reaches it | in | `0084`, `0042` |
| `has-no(L, D)` | which concepts have no covering artifact | a crossing finds only what is present; no chain reaches an absence | in | `0003` |
| `MOVE(L, D)` | which concepts does this obligation require | `has(L, D)` says only that a kind of link exists, not to whom | in | `0046`, `0096` |
| `MOVE` with `L`, `D` omitted | which of X's neighbours are worth a look | nine chains, one per kind, and their union is not a chain | in the domain; **not a separate surface verb** - `look_at`'s `<neighbours>` composes it (`0096`), and a second name for it fails `0024` | `0096` |

**The check #84's charting comment set is passed on the test's own terms:** `nodes_without(kind, link_kind, direction)` is `START(kind) · FILTER(has-no(link_kind, direction))`, and the atom fell out of *"which concepts have no covering artifact"* under the vocabulary, with `0003` as its instance and its derivation from `0001`'s third job untouched. `closure` is `REPEAT`. Whether either is a separately named operation is #88's.

**#16's second membership test, ruled here as routing's criterion on a row.** *A field belongs in ring 0 iff, without it, the coordinator cannot decide where to look next* becomes: **a field belongs in a routing result's per-kind set if and only if, without it, the coordinator cannot form its next intent or cannot decide whether to spend the next call.** This is the criterion; which fields meet it for `obligation` in ring 0 is the render's selection clause, applied at #82 with #86 supplying which judgments the coordinator must be able to make. #16's first test - *an observation earns its place iff a judgment demonstrably changes when it is present* - is the general form of which this is the instance for one judgment; it needs an observation to apply and stays at #16 with its wake unchanged.

### 5. The HNSW verdict - deliverable 4

**Scaffolding. Removed from #84's body.** The analogy failed on its subject, not on the two reservations the body recorded: HNSW is an **index structure for similarity retrieval**, and what this system needed named is a **query model over typed links**. Its descent story - enter sparse, go dense - describes the coordinator's loop (fetch, form an intent, resolve, fetch), which is not routing; routing is one half of that loop.

**Replaced by a commitment: the skeleton is a property graph and routing is a traversal over it.** Labelled nodes (`kind`), typed directed links with fields (`role`, `locator`), and §2's steps map one-for-one onto a graph database's traversal steps: `START(K)` is `V().hasLabel(K)`, `START(ref)` is `V(id)`, `FILTER` is `.has()`, `has-no(L, D)` is `.not(outE(L))` - a filter step there too - `MOVE(L, D, Q)` is `.outE(L).has(Q).inV()`, `REPEAT` is `.repeat(out(L))`. `0059`'s persistence tier already holds the two primitives, *fetch-by-key and one-hop traversal*. The commitment's value is that it states #84's asymmetry in one line: the write side is `addV / addE / property` (`0088`'s `set / attach / detach`), the read side is `V(id)` and no traversal.

**The commitment is bounded by the deviations, each a ruling the commitment may not override:**

| a graph database | this system | record |
|---|---|---|
| an edge requires both endpoints; delete cascades | a ref may dangle; nothing cascades | `0018` |
| an edge's identity is a surrogate; properties update | identity is the natural key with `locator`, for idempotent re-landing; no update, detach + attach; an `id` for addressing only | `0017` `0096` |
| schema optional or loose | link kinds a closed set with endpoint signatures; a compiler refuses | `0012` `0063` |
| membership is an edge | course membership is a field | `0029` |
| time on vertices | no time axis in the skeleton | `0021` |
| labels are flat | three semantic layers | `0009` `0027` |
| an engine with a planner | files plus an adjacency index rebuilt at load | `0062`, repaired in §9 |
| a vector index on the graph | two persisted things coupled by one field | `0019` |
| any caller, full depth | an observation contract: symmetry, discard, residency by policy | `0039` `0043` `0044` |
| every traversal renders | `applies` *"is never rendered"* (`CONTEXT.md`); a crossing over it feeds `REPEAT` and is not shown | `CONTEXT.md` |

The ninth row is the boundary of the whole analogy: a graph database has no concept of what its caller may hold, and half of this repository's records are about that. The commitment covers the skeleton and routing; it does not cover the system. **Swapping in an engine is refused on this table**: an engine provides planning and transactions, which `0062`'s size and the single-writer contract do not need, and it requires the opposite of the first two rows.

### 6. What this makes ring 0

**Ring 0 is one standing routing result, held resident by policy.** Its intent is `START(obligation) · FILTER(admission)`, where admission is today `0042`'s three triggers - expressible in §2's predicate language as two ranges and a disjunction. Two of `0100`'s four clauses are routing's: **admission** is that `FILTER`'s predicate, and **refresh** (`0089`) is re-running the standing intent. The other two are the render's: **selection** is which per-kind fields a row carries, and **arrangement** is the row order and grouping; both belong with ring 0's render at #82, under §4's criterion, with #86 supplying the judgments the rows must serve. `0100` found no clause derived from the purpose because *"what is undefined is routing"*; with routing defined, admission and refresh are generated and the render's two are given their criterion.

Why resident rather than re-run: spontaneity needs somewhere to stand when nothing has been fetched, and `0043` drops what is fetched, so the standing result is held by **policy** - which is what `0019` already says ring 0 is. A ring 0 row is a routing result member rendered ring 0's way; it is not a line (`0082`: the line is a *"transfer of the field set, not of a render"*; `0096`: `has-more` survives only in ring 0).

**`0021`'s time projection is another standing routing result** - *"a separate projection over the skeleton the way ring 0 is"* - so a projection is a result, not a persisted thing, and **what routing ranges over is the persisted things**: the skeleton, and the store if #87 admits by-handle. The body's fog patch on a below-skeleton layer waited on routing's output type. The output is a set of addresses and nothing in it enters a layer, so the HNSW-shaped form of that question - *where does routing enter the next layer down* - dissolves. Whether a further persisted thing exists at all is a different question; it stays in #84's fog restated without the HNSW framing, and it is upstream of #66 as #84 already records.
