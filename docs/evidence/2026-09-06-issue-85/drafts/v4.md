### 1. Definition

**Routing is the resolving half of the query: a system-held function from an intent to the set of paths that satisfy it.**

```
routing : intent -> { path }
```

The query has two halves. **Fetch** takes an address and returns its render - `look_at(id)`, a read, not routing. **Resolve** takes an intent the caller can state in the skeleton's structural vocabulary and returns the paths that satisfy it, each ending at an address. Routing is resolve.

**Who holds what.** The system holds routing, and holds by policy one standing intent whose result is ring 0 (§6). The coordinator holds the intent it forms and that one result resident. A dispatch target holds nothing (`CONTEXT.md`, *holder*). No new holder is introduced.

**Spontaneity, restated as a mechanism.** Routing is not prompt-driven, and *unprompted* does not mean *without the owner*: it means **the intent must be formable from the vocabulary plus what the current render exposes**. The vocabulary's closed sets - the kinds, the link kinds and their signatures (`0012`) - reach the coordinator through the tool description (#79). Which of them apply *here* reaches it in-band: `0098` spells names back, `0092`'s `has-more` lists a node's link kinds, `0096`'s `<edge>` carries `type` and `direction`. So `look_at` is this system's introspection over a vocabulary the coordinator already has.

**What routing is not.** Not a search (`0046`: the coordinator *"does not search the corpus"*); not the delivery of an answer (that is fetch); not a judgment of importance (a judgment is made *with* operations and can never be an element of an operation set); not a statement about renders (what a render must carry so that an intent can be formed from it is stated here as a criterion, §4; what it looks like is downstream). Mechanistic reachability - that a path exists in the skeleton - is a property of the schema and not routing's; it is deliberately not universal, since two unrelated nodes may coexist.

### 2. Input - deliverable 1

**Routing's input is one intent, stated in the skeleton's structural vocabulary.** Not *ring 0 plus the skeleton index* as the body guessed - that is what the coordinator sees, not what routing consumes.

**The vocabulary.** A **node** is a kind, an id and that kind's field set, and `kind` is itself a field on the node (`0027`); a **layer** is one of three kinds and names the same set as that kind today; a field may be **Ref-typed**, naming another node (`0018`: `Ref := (kind, id)`, resolvable without a lookup); a **link** is its own record, `from · to · kind · role? · locator?` (`0017`), never a field on either end (`0016`); **link kinds** are a closed set with endpoint signatures (`0012`); **direction** is `points-at` or `pointed-by` (`0096`); an **annotation** is a node kind reached by an `about` link (`CONTEXT.md`). The vocabulary contains no set operations and no content.

**What that vocabulary can describe.** A set can be named by kind; by a Ref; by a predicate over a node's fields, where the field's type decides the comparisons and boolean connectives join them; by following a link kind in a direction to the other end, optionally filtering on the link's own fields first; by following a Ref-typed field to the node it names, or back from a node to the nodes whose field names it; by repeating a crossing; and - since a link is a record of its own and an annotation is a node of its own - **by a predicate that reaches those records**, which is a sub-chain used as a test. Nothing else in the vocabulary names a set.

**The domain, as chain steps and a predicate language:**

```
START(K)                 every node of kind K
START(ref)               the node this (kind, id) names, or nothing
FILTER(P)                keep the members satisfying P
MOVE(L?, D?, Q?)         cross links of kind L in direction D; Q filters on the link's fields first;
                         L and D omitted means every kind, both directions
MOVE(field, D)           cross a Ref-typed field: points-at reaches the node it names,
                         pointed-by reaches the nodes whose field names this one
REPEAT(MOVE)             cross zero or more times

P ::= <field> <comparison> <value>     a comparison the field's type admits
    | exists(chain)                     a sub-chain from the member is non-empty - the join
    | not P  |  P and P  |  P or P
```

**Composition is chaining**: each step's output is the next step's input, in one call. A predicate's `exists(chain)` is the same chaining used as a test on one member, and it is what lets an intent reach a link's other end, an annotation's field, or a specific neighbour: *has a `covers` link inbound* is `exists(MOVE(covers, pointed-by))`; *has none* is `not exists(...)`; *is required by B* is `exists(MOVE(requires, pointed-by) · FILTER(id = B))`. Set operations are not composition; the connectives cover conjunction and disjunction inside a step, and `exists` covers what intersection and difference would have served.

**Two starts, and one extensional identity.** `START(ref)` names the same set as `START(K) · FILTER(id = X)`; both are kept because spontaneity starts from ring 0, which is a set of rows and not a node, so its first intent is `START(K)`, while a prompted walk from a node the coordinator is looking at is `START(ref) · MOVE`. A ring 0 row carries an id (`0025`), so an intent formed from ring 0 may also anchor.

**An address** is a handle the query accepts: today a node's `id` and an edge's `id` (`0096`, `0097`). Whether a chunk's handle is one is #87's.

**Outside the domain by type:** an intent by content. `P` has no content atom, so *things about X* cannot be stated. Who serves such an intent, and with what, is #87's.

**A candidate step this vocabulary places but does not admit:** the store's by-handle read, *"the chunks a known node points at"* (`CONTEXT.md`). A chunk is not a node and the coupling is one field, `chunk.node_id` (`0019`), so it is a step onto the other persisted thing. Whether it enters routing's domain, and whether a chunk's handle is an address, is #87's.

**Not decided here:** the spelling of any step (`0070`, `0093`); whether the two starts, or any step, are one surface verb or several (the grammar - #84's *Destination* names it a later decision); the values `points-at` / `pointed-by` as written-back names, which `0098` classes as *invented here → free* and which an intent would carry back (#79's); whether an edge's `id` shares the node id space, which no record states.

### 3. Output - deliverable 2

**Routing returns a set of paths.** A path is the chain a member arrived by - node, link, node, … - ending at an address, and the endpoint carries what decides whether it is worth the next call. Paths, not endpoints, because a judgment across obligations is a judgment about their **relations** (`0100` grounds the flat-render defect on `0001`'s second job, *"a statement about relations across obligations"*), and a set of endpoints has no position for a relation: `START(obligation) · MOVE(requires) · MOVE(requires, pointed-by)` as endpoints is `{A, B, D}` with the pairing gone; as paths it is *A - requires → c - requires ← B* and the judgment can be made. Deduplication is by path, so a member reached over four links (`0017`'s deck citing the textbook four times) is four paths. A one-step chain's paths are the endpoints with the link they were reached by; `START(K)`'s paths are its members.

**Not bare ids.** An assigned id *"says nothing about the record it names"* (`CONTEXT.md`, `id`; `course.id` is supplied, `0026`), so an endpoint alone gives no basis to decide. Which fields decide the call for an obligation is the selection question, downstream (§6); for a `concept` or `artifact` endpoint the field set is the debt `CONTEXT.md`'s `the line` entry records against #17, #19 and #20.

**The set is symmetric by construction.** Every path carries the same shape and no depth, so `0039`'s symmetry - the same observation for every member of the judgment's set - is met by the output type. Depth about any endpoint is fetch's, or dispatch's. **Affordability is a separate question the type does not answer**: a resolve over a whole kind may be too wide to hold, and what happens then - a narrower intent, a bound, or dispatch of the whole - is the *owed length bound* `0039` names as load-bearing (#12 item 6) and is not decided here (§10).

**The set is unordered.** Arrangement is ring 0's own clause and is downstream (§6).

**The body's trichotomy is not three alternatives.** The output is a set of paths. *Dispatch* is the form `0039` selects when depth about a member is unaffordable. *Layer entry* is an intent over a different persisted thing, not a different kind of output. Nothing routing returns is an entry point into anything.

**An empty result names what it ranged over** - the kind, the source, the link kind. `0081` requires a negative answer to name the boundary it speaks for; routing's boundary is its range, and *not in the store* is a separate holder's answer.

**Cost.** `START(ref) · MOVE` is O(degree) (`0046`); `START(K)` is O(kind); `exists(chain)` costs one sub-chain per member. Ring 0's roughly-55 is one such result; it carries `0038`'s scope clause and the fall26 caveat.

### 4. The necessity test - deliverable 3

**The premise, ruled here.** A judgment ranges over a set, and the set must arrive in one return. The ground is Billy's effectiveness constraint, recorded here for the first time: **the coordinator's call count may not grow with the graph.** A set assembled across calls costs one call per piece. No landed record states this premise; it is a ruling of this ticket and travels into the record §9.5 proposes. Whether dispatch calls count against it is not decided here.

> **A step or atom belongs in routing's domain if and only if some judgment the coordinator must make ranges over a set that no finite chain of the other steps and atoms produces in one return - where *other* excludes the step under test everywhere, inside `exists` included.**

**Standing of the test.** It is ruled as the instrument the sibling tickets apply. A finding at #86, #87 or #88 that the test admits what it should not, or excludes what it should not, revises the test and is recorded against it; the test is not a fixed point the findings must conform to.

**A stated limit.** The test admits by extension. Two spellings of the same set are one operation to it, so it does not distinguish `START(K) · FILTER(id = X)` from `START(ref)`, and it must not be read as deciding that either spelling is absent from a surface. Under paths, `MOVE(L, D)` and `START(K) · FILTER(exists(MOVE(L, D')))` are not two spellings of one set: the first returns the crossing, the second does not.

| `START(ref)` | the neighbours of this obligation | `START(K) · FILTER(id = X)` produces the same set | a spelling; the grammar keeps or drops it | `look_at`'s parameter |

Whether either is a separately named operation is #88's.

**#16's second membership test, ruled here as routing's criterion on a path's endpoint.** *A field belongs in ring 0 iff, without it, the coordinator cannot decide where to look next* becomes: **a field belongs on a routing result's endpoint if and only if, without it, the coordinator cannot form its next intent or cannot decide whether to spend the next call.** This is the criterion; which fields meet it for ring 0's rows is downstream (§6). #16's first test - *an observation earns its place iff a judgment demonstrably changes when it is present* - is the general form of which this is the instance for one judgment; it needs an observation to apply and stays at #16 with its wake unchanged.

### 5. The HNSW verdict - deliverable 4

**Scaffolding. Removed from #84's body.** The analogy failed on its subject, not on the two reservations the body recorded: HNSW is an **index structure for similarity retrieval**, and what this system needed named is a **query model over typed links**. Its descent story - enter sparse, go dense - describes the coordinator's loop (fetch, form an intent, resolve, fetch), which is not routing; routing is one half of that loop.

**Replaced by a commitment: the skeleton is a property graph and routing is a traversal over it.** §2's steps map one-for-one onto a graph database's traversal steps: `START(K)` is `V().hasLabel(K)`, `START(ref)` is `V(id)`, `FILTER` is `.has()`, `exists(chain)` is `.where(__.…)` - a filter step carrying a sub-traversal - `MOVE(L, D, Q)` is `.outE(L).has(Q).inV()`, `REPEAT` is `.repeat(out(L))`, and the path output is `.path()`. `0059`'s persistence tier already holds *fetch-by-key and one-hop traversal*. The commitment's value is that it states #84's asymmetry in one line: the write side is `create / attach / set` (`0093`'s primitives); the read side is `V(id)` with one hop composed into it and no traversal as an operation.

**The commitment is bounded by the deviations, each a ruling the commitment may not override:**

| a graph database | this system | record |
|---|---|---|
| an edge requires both endpoints; delete cascades | a ref may dangle; nothing cascades | `0018` |
| an edge's identity is a surrogate; properties update | identity is the natural key with `locator`, for idempotent re-landing; no update, detach + attach; an `id` for addressing only | `0017` `0096` |
| schema optional or loose | link kinds a closed set with endpoint signatures; a compiler refuses | `0012` `0063` |
| membership is an edge | course membership is a Ref-typed **field** (`0029`, on cardinality; its changed status is held at `0084`). For routing a Ref-typed field is crossable (§2's `MOVE(field, D)`, generalising `0084`'s composition); `0029`'s ground is untouched | `0029` `0084` |
| time on vertices | no time axis in the skeleton | `0021` |
| labels are flat | three semantic layers | `0009` `0027` |
| an engine with a planner | files plus an adjacency index rebuilt at load | `0062`, repaired in §9 |
| a vector index on the graph | two persisted things coupled by one field | `0019` |
| any caller, full depth | an observation contract: symmetry, discard, residency by policy | `0039` `0043` `0044` |
| every traversal renders | `applies` *"feeds closure and is never rendered"* (`CONTEXT.md`); a path over it is a result and is not shown as a block's neighbour | `CONTEXT.md` |

The ninth row is the boundary of the whole analogy: a graph database has no concept of what its caller may hold, and half of this repository's records are about that. The commitment covers the skeleton and routing; it does not cover the system. **Swapping in an engine is refused on this table**: an engine provides planning and transactions, which `0062`'s size and the single-writer contract do not need, and it requires the opposite of the first two rows.
